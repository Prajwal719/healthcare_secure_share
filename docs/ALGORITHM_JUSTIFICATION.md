# Algorithm Justification

This document explains every cryptographic algorithm choice in the Secure Healthcare File-Sharing Protocol, with references to standards and academic literature.

---

## 1. AES-256-GCM — File Encryption

**What it does:** Encrypts file plaintext and produces an authentication tag that covers both the ciphertext and the Associated Data (AAD).

**Why AES-256 (not AES-128):**
- AES-128 provides 128-bit security; AES-256 provides 256-bit security.
- NIST SP 800-57 Part 1 Rev 5 classifies AES-256 as "security strength ≥ 256 bits", suitable for protecting data beyond 2031.
- Healthcare data may need to remain confidential for decades; the extra key length provides a safety margin against future cryptanalytic advances.

**Why GCM (not CBC, CTR, or CCM):**
- GCM is an AEAD (Authenticated Encryption with Associated Data) mode. It provides **confidentiality AND integrity** in a single primitive, eliminating the need for a separate MAC and the associated "encrypt-then-MAC vs MAC-then-encrypt" debate.
- CBC without a MAC is vulnerable to padding oracle attacks (POODLE, Lucky13). CBC with HMAC requires careful ordering and is error-prone.
- CCM is also AEAD but requires the message length to be known in advance (not suitable for streaming) and is slower than GCM on hardware with AES-NI.
- GCM is hardware-accelerated on all modern x86/ARM CPUs (AES-NI + CLMUL instructions), making it the fastest secure option.
- Reference: NIST SP 800-38D, "Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM)".

**Why 96-bit nonce:**
- NIST SP 800-38D §5.2.1.1 states that 96-bit IVs are the "recommended" length for GCM because they map directly to the counter block without an additional GHASH computation, preserving the tight security proof.
- Nonces are generated by `os.urandom(12)` (OS CSPRNG) — never reused with the same key.

**Why a fresh key per file:**
- Reusing a GCM key+nonce pair is catastrophic: it reveals the XOR of the two plaintexts and allows forgery of authentication tags.
- Generating a fresh 256-bit key per file (also via `os.urandom(32)`) makes nonce reuse structurally impossible.

**Why AAD binding:**
- The GCM tag covers the AAD without encrypting it. We bind `{sender_id, filename, timestamp}` as AAD so that an attacker cannot re-attach a ciphertext to a different file record or claim a different sender — the tag will fail.

## 2. RSA-3072-OAEP — Key Wrapping

**What it does:** Encrypts the per-file AES-256 key under each recipient's RSA public key.

**Why RSA-OAEP (not RSA-PKCS#1 v1.5):**
- PKCS#1 v1.5 encryption is vulnerable to the Bleichenbacher adaptive chosen-ciphertext attack (1998) and its modern variants (ROBOT attack, 2018). These attacks allow an attacker who can query a decryption oracle to recover the plaintext.
- OAEP (Optimal Asymmetric Encryption Padding) is provably IND-CCA2 secure under the RSA assumption in the random oracle model (Bellare & Rogaway, 1994).
- Reference: RFC 8017 (PKCS#1 v2.2), NIST SP 800-56B Rev 2.

**Why SHA-256 for OAEP hash and MGF1:**
- SHA-1 is deprecated for all new applications (NIST SP 800-131A Rev 2, 2019).
- SHA-256 provides 128-bit collision resistance, matching the security level of AES-256.

**Why 3072-bit RSA:**
- NIST SP 800-57 Part 1 Rev 5 places 3072-bit RSA in security category "≥ 128 bits" (matching AES-256).
- 2048-bit RSA provides only ~112-bit security and is approved only through 2030.
- 4096-bit RSA would provide a larger margin but is ~3× slower for key operations; 3072-bit is the recommended balance.

**Why wrap per recipient (not re-encrypt per recipient):**
- The file is encrypted once. Sharing with N recipients costs N RSA operations (cheap, ~1 ms each) rather than N AES re-encryptions of potentially large files.
- Revoking access means deleting one database row (the wrapped key), not re-encrypting the file.
- This is the standard "hybrid encryption" pattern used in PGP, S/MIME, and CMS (RFC 5652).

## 3. RSA-3072-PSS — Digital Signatures

**What it does:** The uploader signs `(ciphertext ‖ nonce ‖ AAD)` with their RSA private key. The server and recipient verify the signature.

**Why RSA-PSS (not RSA-PKCS#1 v1.5 signatures):**
- PKCS#1 v1.5 signatures have no known full break but lack a formal security proof. PSS (Probabilistic Signature Scheme) is provably secure in the random oracle model (Bellare & Rogaway, 1996).
- FIPS 186-5 (2023) mandates PSS for all new RSA signature applications and deprecates PKCS#1 v1.5 signatures.
- Reference: RFC 8017 §8.1, FIPS 186-5.

**Why sign the full `(ciphertext ‖ nonce ‖ AAD)` tuple:**
- Signing only the ciphertext would allow an attacker to detach the nonce or AAD and substitute different values (the GCM tag would catch this, but defence-in-depth requires the signature to cover all fields).
- Binding all three fields ensures the signature provides both **authentication** (who uploaded) and **non-repudiation** (the uploader cannot deny it).

**Why MAX_LENGTH PSS salt:**
- A longer PSS salt provides a tighter security reduction. `padding.PSS.MAX_LENGTH` sets the salt to the maximum allowed by the key size (32 bytes for SHA-256), providing 256 bits of randomness in the signature.

## 4. scrypt — Password Hashing

**What it does:** Derives a 256-bit key from a user's password and a random salt for storage and verification.

**Why scrypt (not bcrypt or PBKDF2):**
- bcrypt is CPU-hard but not memory-hard; modern GPUs can compute ~100,000 bcrypt hashes/second.
- scrypt is **memory-hard**: each computation requires O(N × r × 128) bytes of RAM. With N=2^17, r=8, this is 16 MiB per hash — making GPU/ASIC attacks ~1000× more expensive than bcrypt.
- PBKDF2-HMAC-SHA256 is also not memory-hard; it is included as a spec-required alternative.
- Reference: Colin Percival, "Stronger Key Derivation via Sequential Memory-Hard Functions" (2009); OWASP Password Storage Cheat Sheet (2023).

**Parameters (N=2^17, r=8, p=1):**
- N=2^17 (131,072): CPU/memory cost factor. OWASP 2023 recommends N ≥ 2^17 for interactive logins.
- r=8: block size multiplier (standard value).
- p=1: parallelisation factor (single-threaded; increase for offline key derivation).

**Why constant-time comparison:**
- `hmac.compare_digest()` runs in time proportional to the length of the inputs, not the position of the first differing byte. This prevents timing side-channel attacks where an attacker measures response times to learn the prefix of the stored hash.

## 5. HMAC-SHA256 — Session Tokens

**What it does:** Signs session token payloads so the server can verify them without a database lookup.

**Why HMAC (not RSA-PSS for tokens):**
- Tokens are issued AND verified by the same server — symmetric HMAC is the correct primitive for this use case.
- RSA-PSS would be appropriate only if a third party (e.g., a microservice) needed to verify tokens without the secret key.
- HMAC-SHA256 is ~1000× faster than RSA signing, which matters for high-frequency token verification.

**Why in-memory key (not stored on disk):**
- The HMAC key is generated by `os.urandom(32)` at server startup and never persisted.
- This means all tokens are automatically invalidated on server restart — a desirable property in a healthcare context (no stale tokens survive a server crash or restart).

---

## 6. Mutual TLS (mTLS)

**Why mutual TLS (not one-way TLS):**
- Standard TLS authenticates only the server. mTLS requires the client to also present a certificate signed by the trusted CA.
- This prevents any unauthorised client from even opening a connection, providing a network-layer authentication layer independent of the application-layer login.
- In a healthcare context, this ensures that only hospital-issued devices (with CA-signed certs) can connect.

**Why TLS 1.2 minimum (prefer 1.3):**
- TLS 1.0 and 1.1 have known vulnerabilities (POODLE, BEAST, CRIME) and are deprecated by RFC 8996 (2021).
- TLS 1.2 with strong cipher suites is secure; TLS 1.3 removes legacy cipher suites and provides mandatory forward secrecy.
- `ssl.SSLContext.minimum_version = ssl.TLSVersion.TLSv1_2` enforces this at the Python level.

---

## 7. Replay Protection (Three-Layer)

**Why three independent layers:**
- **Timestamp** (±30 s window): Rejects messages that are too old or too far in the future. Alone, it allows replay within the 30-second window.
- **UUID message ID** (bounded LRU cache): Rejects exact duplicates. Alone, the cache must be unbounded or have a complex TTL.
- **Monotonic counter** (per session): Rejects out-of-order or replayed messages within a session. Alone, it requires reliable per-session state.
- Combining all three provides defence-in-depth: any single layer can fail independently without creating a replay vulnerability.

---

## 8. Hash-Chained Audit Log

**Why hash chaining:**
- Each entry's hash incorporates the previous entry's hash (like a blockchain). Modifying any past entry changes its hash, which no longer matches the `prev_hash` in the next entry — the mismatch propagates forward.
- `verify_audit_log()` walks the entire chain and detects the first broken link.
- This mirrors the structure used in Git (commit hashes), Certificate Transparency (RFC 6962), and blockchain systems.

**Why SHA-256 for the audit log (not a password hash):**
- SHA-256 is appropriate here because we are hashing log entries (structured data), not passwords. The prohibition on "plain SHA-256 for passwords" in the spec applies only to password storage, where an attacker can precompute rainbow tables. Log entries are not subject to dictionary attacks.
